# بریف کار برای Antigravity (بک‌اند)

این سند را کامل به Antigravity بدهید. نقش‌ها: **Antigravity بک‌اند را می‌نویسد؛ Claude ناظر است** و فقط نتیجه‌ی `npm run review` را بررسی می‌کند. اگر ایرادی باشد، Claude یک پرامپت اصلاحی می‌دهد که شما به Antigravity برمی‌گردانید.

## پروژه در یک نگاه

«پلتفرم رشد نخبه»: سامانه آموزشی و مدیریتی کانون برای حدود ۵۰۰ دانش‌آموز پایه چهارم تا نهم. نقش‌ها: دانش‌آموز، معلم، مدیر کانون، والدین، مدیر سامانه. همه‌چیز فارسی و راست‌به‌چپ است.

- **زبان و اجرا:** Node.js (حداقل ۲۲.۱۳)، ES modules، بدون فریم‌ورک.
- **پایگاه داده:** SQLite داخلی Node (`node:sqlite`)، هم‌زمان (sync) و فقط در حلقه رویداد اصلی.
- **ساختار:** `server/index.js` (ورودی)، `server/routes/*.js` (API هر نقش)، `server/logic.js` (امتیاز، رتبه، قفل پنل)، `server/db.js` (طرح و ایندکس)، `server/util.js`، `server/http.js`، `scripts/` (ابزارها)، `deploy/` (استقرار).
- **مستند کامل:** `README.md`، به‌خصوص بخش «راه‌اندازی روی سرور واقعی» و جدول متغیرهای محیطی.

## مرزهای سخت (نقض = ردشدن)

1. **فقط این مسیرها را تغییر بدهید:** `server/`، `scripts/`، `deploy/`، `docs/`، `README.md`، `package.json` (فقط بخش scripts)، `.gitignore`. به `public/` (فرانت‌اند) دست نزنید؛ اگر یک کار به تغییر فرانت‌اند نیاز دارد، فقط قرارداد API را در توضیح commit بنویسید و Claude سمت رابط کاربری را می‌سازد.
2. **هیچ وابستگی npm اضافه نکنید.** پروژه عمداً بدون `node_modules` است. از `fetch`، `node:crypto`، `node:sqlite` و بقیه‌ی کتابخانه‌ی استاندارد Node استفاده کنید.
3. **پاسخ‌های API موجود را نشکنید.** فرانت‌اند به قالب فعلی وابسته است. فقط می‌توانید فیلد اضافه کنید، نه حذف یا تغییر نام.
4. **پایگاه داده‌ی واقعی وجود خواهد داشت.** هر تغییر طرح باید *افزایشی و ایمن* باشد (جدول یا ستون جدید با مهاجرت)، نه حذف و ساخت دوباره. `npm run seed` را روی داده‌ی واقعی اجرا نکنید.
5. **حلقه رویداد را قفل نکنید.** کارهای سنگین (هش رمز، شبکه، فایل بزرگ) باید ناهمزمان باشند. الگوی هش ناهمزمان در `server/util.js` هست.
6. **رمز، کلید و داده‌ی شخصی را در لاگ ننویسید.** فایل‌های `data/`، `uploads/` و `.env` را commit نکنید.
7. **تست‌ها را ضعیف نکنید.** در `scripts/smoke.mjs` فقط می‌توانید بررسی اضافه کنید، نه حذف یا نرم کنید.

## روش کار و تحویل

- برای هر کار یک شاخه جدا: `ag/T2-password-change` و مانند آن. به `main` مستقیم push نکنید.
- هر کار یک commit (یا چند commit مرتب) با توضیح فارسی.
- **قبل از تحویل `npm run review -- --base main` را اجرا کنید** و خروجی کامل را در توضیح commit بچسبانید. باید «نتیجه: تأییدشده» بدهد.
- برای هر ویژگی تازه، بررسی‌هایش را به `scripts/smoke.mjs` اضافه کنید (دسترسی هر نقش، حالت خطا، تکرار درخواست).
- ابزارهای کمکی: `npm run smoke` (۶۳+ بررسی)، `npm run loadtest -- --users 500` (تست بار)، `npm run init`، `npm run import`.

## فهرست کارها (به ترتیب اولویت)

### T1. سامانه مهاجرت پایگاه داده (پیش‌نیاز بقیه)
در `server/db.js` مهاجرت‌ها را با `PRAGMA user_version` و یک آرایه مرتب از تابع‌ها بسازید. هر مهاجرت یک‌بار اجرا شود و داخل تراکنش باشد. باید روی پایگاه داده‌ی قدیمی و فعلی (بدون `user_version`) بدون ازدست‌رفتن داده کار کند.
**قبول:** روی یک نسخه پشتیبان از `data/roshd.db` اجرا شود و `npm run smoke` همچنان بگذرد؛ اجرای دوباره چیزی تغییر ندهد.

### T2. اجبار تغییر رمز در اولین ورود
چرا: رمز اولیه دانش‌آموز، کد ملی خودش است و همکلاسی‌ها ممکن است آن را بدانند.
- ستون `users.must_change_password` (پیش‌فرض ۰). مقدار ۱ هنگام ثبت‌نام دستی، ثبت‌نام گروهی (CSV) و بازنشانی رمز توسط مدیر. حساب‌های نمونه‌ی seed تغییری نکنند.
- وقتی ۱ است، فقط `GET /api/me`، `POST /api/me/password` و `POST /api/auth/logout` کار کنند. بقیه کد **۴۰۳** با بدنه `{ error: "...", code: "password_change_required" }` برگردانند.
- `GET /api/me` فیلد `must_change_password` را برگرداند.
- تغییر رمز موفق، پرچم را صفر کند و رمز جدید نباید برابر کد ملی یا شماره موبایل باشد (خطای ۴۰۰ با پیام فارسی).
**قبول:** بررسی‌های تازه در smoke؛ سمت رابط کاربری را Claude می‌سازد.

### T3. دفتر ثبت رویدادهای حساس (audit log)
جدول `audit_log(id, at, actor_id, actor_role, action, target, ip, detail)`. ثبت شود: ورود به پنل کاربر دیگر (impersonate)، تأیید و رد رسید، حذف دانش‌آموز، بازنشانی رمز، تهیه و بازیابی پشتیبان، تغییر تنظیمات کانون و مبلغ حق عضویت. `GET /api/admin/audit?limit=&actor=&action=` فقط برای مدیر سامانه.
**قبول:** بررسی دسترسی در smoke (غیرمدیر → ۴۰۳)؛ درج رویداد در مسیر تأیید رسید؛ لاگ نباید رمز یا `pass_hash` داشته باشد.

### T4. خروجی گرفتن (CSV)
`GET /api/manager/export/{students,attendance,payments,ledger}.csv`: UTF-8 با BOM، ستون‌های فارسی، تاریخ شمسی، فقط داده‌ی کانون خود مدیر. فیلتر بازه تاریخ برای `attendance` و `ledger`.
**قبول:** بررسی در smoke؛ مدیر کانون دیگر نتواند داده‌ی این کانون را ببیند.

### T5. درگاه پرداخت فروشگاه (زرین‌پال، نسخه ۴)
- `POST /api/shop/checkout` وقتی `ROSHD_ZARINPAL_MERCHANT` تنظیم باشد: سفارش با وضعیت `pending` بسازد و `{ payment_url }` برگرداند. وقتی تنظیم نباشد، رفتار فعلی (شبیه‌سازی) بماند.
- `GET /api/shop/callback` را درگاه صدا می‌زند: تأیید (verify) انجام شود، سفارش `paid` شود، کد پیگیری صادر شود و درآمد **فقط یک‌بار** در حسابداری ثبت شود (ایدمپوتنت؛ بازدید دوباره callback چیزی را دوباره ثبت نکند). شکست یا انصراف: `failed`.
- متغیر `ROSHD_ZARINPAL_SANDBOX=1` برای محیط آزمایشی.
- مبلغ را سمت سرور از قیمت محصول محاسبه کنید، نه از ورودی کاربر.
**قبول:** با یک درگاه جعلی داخل تست (سرور موقت) هر دو حالت موفق و ناموفق و callback تکراری آزمایش شود. اتصال واقعی به زرین‌پال را بدون مرچنت نمی‌توان تست کرد؛ این را صریح گزارش کنید.

### T6. اعتبارسنجی روی لینوکس
روی یک سرور اوبونتو: `npm run review`، آزمایش `SIGTERM` (خاموش شدن تمیز و بسته شدن WAL)، اجرای سرویس با `deploy/roshd.service`، و گزارش نتیجه. اگر چیزی ویندوز-محور بود اصلاح کنید.

## چیزهایی که **نباید** انجام شود
- بازنویسی یا فرمت‌کردن کل فایل‌ها (تغییرات باید کوچک و قابل بازبینی باشند).
- تغییر نحوه‌ی ورود یا ساختار توکن جلسه بدون توضیح امنیتی.
- افزودن پردازش پس‌زمینه‌ی سنگین روی حلقه رویداد.
- حذف محدودیت نرخ یا بررسی‌های CSRF در `server/index.js`.
